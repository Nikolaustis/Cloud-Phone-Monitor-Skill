# Public Release Process

## Why staging exists

A developer working tree can legitimately contain local runtime files, private deployment helpers, generated bytecode, or private configuration. Those files must not become public merely because they were not noticed during upload.

The public package therefore uses an **explicit file allowlist**, not a broad directory copy plus exclusions.

## Canonical flow

```text
working tree
  -> behavior tests (bytecode writing disabled)
  -> explicit-allowlist staging
  -> deployment_contract public-field sanitization
  -> staged-source validation
  -> deterministic Manifest generation
  -> Manifest validation
  -> fresh rebuild compared against staged Manifest
  -> validated Manifest copied to working tree
  -> fresh rebuild compared against committed Manifest
  -> deterministic public ZIP
```

The allowlist lives in `tools/public_release_policy.py`. `tools/build_release_staging.py`, the source validator, Manifest generator, release ZIP builder, and CI all consume the same policy.

## Python bytecode hygiene

Release tooling must not mutate the staging tree while validating it. Every release-facing Python entry point sets `sys.dont_write_bytecode = True`; `PREPARE_RELEASE.ps1` and CI also set `PYTHONDONTWRITEBYTECODE=1` and use Python's `-B` switch.

This is deliberate defense in depth. A validator must not create `tools/__pycache__/` and then fail its own exact-tree validation. Tests execute the staged validator without relying on the environment variable and assert that neither `__pycache__` nor `*.pyc` is created.

## Manifest commit semantics

`MANIFEST_SHA256.txt` is not updated until a freshly rebuilt public staging tree has been validated against the staged Manifest. This prevents a failed release attempt from replacing the working-tree Manifest with a value that was never proven reproducible.

After the staged Manifest is copied into the working tree, the release contract is rebuilt once more and compared against the committed Manifest.

## ZIP packaging boundary

`tools/build_release_zip.py` does not blindly zip every file under staging. It accepts only:

- files approved by `tools/public_release_policy.py`; and
- `MANIFEST_SHA256.txt`.

Any unexpected file, symlink, bytecode cache, runtime artifact, or private file makes ZIP creation fail closed.

## Deployment contract

Only these keys are public release contract fields:

```text
schema_version
history_storage
publisher_capability
```

Private remotes or local deployment metadata present in a developer copy of `deployment_contract.json` are not copied to public staging. Release logs report only the number of removed non-public fields, not their values.

## GitHub CI

`.github/workflows/ci.yml` performs three classes of checks:

- Linux release contract: Python tests, private-file rejection, public staging rebuild, bytecode-pollution check, exact allowlist validation, Manifest comparison, and canonical ZIP construction.
- Windows runtime contract: dedicated `.venv` creation, Playwright Chromium launch probe, Windows PowerShell state-machine smoke tests, and Python tests.
- Dashboard build: clean `npm ci` followed by production build.

A release should not be considered complete if the committed `MANIFEST_SHA256.txt` differs from a freshly rebuilt public staging tree.
